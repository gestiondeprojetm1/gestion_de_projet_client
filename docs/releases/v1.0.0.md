# Fiche de mise en production — v1.0.0

## 1. Informations générales

- **Version :** v1.0.0
- **Type de livraison :** Version initiale
- **Fonctionnalité :** Gestion du stock des produits
- **Environnement cible :** Production
- **Responsable du déploiement :** Équipe DevOps
- **Approbateur :** Product Owner / responsable désigné (à confirmer)
- **Statut :** Préparation de la livraison

## 2. Contenu de la livraison

Cette version introduit la gestion du stock des produits.

- Déclaration du stock disponible pour chaque produit.
- Vérification du stock avant validation d'une commande.
- Refus d'une commande lorsque la quantité demandée dépasse le stock disponible.
- Affichage d'un message d'erreur clair en cas de stock insuffisant.

## 3. Déroulement du déploiement

### Étape 1 : Publication de l'image

- Création d'un tag Git au format vX.Y.Z.
- Exécution des tests automatisés et du scan des secrets.
- Construction et publication de l'image Docker sur GHCR.
- Conservation du digest de l'image pour identifier précisément la version publiée.

### Étape 2 : Déploiement en staging

Le workflow GitHub Actions démarre temporairement :
- Une instance PostgreSQL.
- L'API avec l'image Docker publiée.
- Un réseau Docker isolé pour les tests.

La migration de la base de données est exécutée en staging.

### Étape 3 : Smoke test

Vérifications effectuées par le workflow :
- L'API répond sur /health.
- Le statut de l'API est "ok".
- La connexion à PostgreSQL est opérationnelle.
- Une seconde vérification est effectuée après la migration.

Le déploiement est considéré comme validé uniquement si ces contrôles réussissent.

### Étape 4 : Approbation et production

Avant toute mise en production :
- Vérifier les résultats du staging.
- Vérifier les tests automatisés.
- Faire valider la livraison par le responsable désigné.
- Obtenir une approbation humaine avant le déploiement en production.

**Statut actuel :** le déploiement en production et son approbation restent à configurer dans GitHub Actions.

## 4. Risques identifiés

| Risque | Mesure préventive |
|---|---|
| Stock incorrect après une commande | Tester la mise à jour du stock |
| Commande acceptée malgré un stock insuffisant | Ajouter des tests de validation |
| Indisponibilité de l'API après déploiement | Effectuer un test de santé |
| Problème de connexion à PostgreSQL | Vérifier la connexion à la base de données |
| Échec d'une migration | Tester les migrations en staging avant la production |

## 5. Critères Go / No-Go

### GO

- Tous les tests automatisés passent.
- Le scan des secrets ne détecte aucun secret.
- L'image Docker est construite et publiée correctement.
- L'API répond sur /health en staging.
- La connexion à PostgreSQL fonctionne.
- La migration et le smoke test réussissent.
- L'approbation du responsable est obtenue.
- Une image précédente utilisable pour le rollback est disponible.

### NO-GO

- Un test critique échoue.
- Un secret est détecté.
- L'API ne répond pas.
- La base de données est inaccessible.
- Une migration échoue.
- La gestion du stock présente une anomalie.
- L'approbation n'est pas obtenue.
- Aucun retour arrière fiable n'est possible.

## 6. Plan de retour arrière (Rollback)

En cas d'échec après le déploiement :

1. Déclencher la procédure de rollback par le responsable DevOps.
2. Identifier le digest de la dernière image stable.
3. Arrêter la nouvelle version.
4. Redéployer l'image Docker précédente.
5. Vérifier la disponibilité de l'API sur /health.
6. Vérifier la connexion à PostgreSQL.
7. Confirmer le retour au fonctionnement normal.

- **Responsable :** Équipe DevOps.
- **Objectif :** rollback en moins de 5 minutes.
- **Vérification :** contrôle de santé de l'API et de la base de données.

**Limite :** le retour à l'ancienne image ne garantit pas l'annulation des modifications déjà effectuées dans la base de données. Les migrations doivent donc être conçues pour limiter les risques de perte ou d'incompatibilité des données.

**Prérequis :** une image stable précédente doit être disponible. Pour une première livraison, cette condition doit être vérifiée avant d'autoriser la production.

## 7. Validation et approbation

- **Responsable du déploiement :** Équipe DevOps.
